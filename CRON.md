# Зовнішній тригер: щоденний запуск брифу

Планувальник GitHub на безкоштовному тарифі ненадійний — за весь час він
спрацював один раз із багатьох. Тому основним запуском стає зовнішній
сервіс, який щоранку викликає GitHub через API.

Власний розклад GitHub лишається як підстраховка на 04:25 і 05:40 UTC.
Якщо зовнішній тригер спрацює першим, ці запуски побачать готовий випуск
і мовчки вийдуть.

---

## Крок 1. Створити токен GitHub

Токен потрібен, щоб сторонній сервіс мав право запускати воркфлоу.

1. **github.com** → аватар у правому верхньому куті → **Settings**
   (це налаштування акаунта, не репозиторію)
2. У самому низу лівого меню → **Developer settings**
3. **Personal access tokens** → **Fine-grained tokens** → **Generate new token**
4. Заповніть:
   - **Token name**: `news-brief-cron`
   - **Expiration**: 1 рік (або без обмеження, якщо доступно)
   - **Repository access**: **Only select repositories** → виберіть `news-brief`
   - **Permissions** → **Repository permissions** → знайдіть **Actions** →
     поставте **Read and write**
5. **Generate token**

Токен показується **один раз**. Скопіюйте його одразу — почнеться з
`github_pat_`.

> Дрібно-гранульований токен обмежений одним репозиторієм і однією
> здатністю: запускати воркфлоу. Навіть якщо він витече, більше нічого
> зробити ним не можна.

---

## Крок 2. Зареєструватись на cron-job.org

Безкоштовно, без картки, сервер у Німеччині.

1. Відкрийте **cron-job.org** → **Sign up**
2. Підтвердіть пошту, увійдіть

---

## Крок 3. Створити завдання

**Create cronjob** і заповніть так.

**Вкладка Common:**

| Поле | Значення |
|---|---|
| Title | Ранковий бріф |
| URL | `https://api.github.com/repos/ВАШ-ЛОГІН/news-brief/actions/workflows/brief.yml/dispatches` |
| Schedule | Every day at **07:00**, часовий пояс **Europe/Kyiv** |

Часовий пояс важливий: якщо вкажете Київ, сервіс сам врахує перехід на
зимовий час, і бріф приходитиме о сьомій цілий рік. Це головна перевага
над cron у GitHub, який знає лише UTC.

**Вкладка Advanced:**

- **Request method**: `POST`
- **Headers** — додайте три рядки:

| Key | Value |
|---|---|
| `Authorization` | `Bearer ВАШ_ТОКЕН` |
| `Accept` | `application/vnd.github+json` |
| `X-GitHub-Api-Version` | `2022-11-28` |

- **Request body**:

```json
{"ref":"main","inputs":{"source":"cron"}}
```

Поле `source: cron` обов'язкове. За ним пайплайн розуміє, що це
автоматичний запуск, і вмикає захист від дубля. Без нього кілька спроб
дали б кілька брифів за ранок.

- **Content-Type**: `application/json` (якщо є окреме поле)

Збережіть.

---

## Крок 4. Перевірити одразу

Не чекайте ранку. У списку завдань натисніть **Run now** (або **Test run**).

**Успіх виглядає так:** сервіс показує відповідь **204 No Content**. Це
нормально — GitHub на цей виклик не повертає тіла. Одразу після цього в
Actions має з'явитись новий запуск.

**Найчастіші помилки:**

| Відповідь | Причина |
|---|---|
| 401 | токен неправильний або без `Bearer ` перед ним |
| 403 | у токена немає права **Actions: Read and write** |
| 404 | помилка в логіні, назві репозиторію або імені файлу воркфлоу |
| 422 | помилка в тілі запиту або гілка не `main` |

---

## Що буде далі

| Час | Що відбувається |
|---|---|
| 07:00 Київ | cron-job.org викликає GitHub |
| 07:00 | воркфлоу стартує, перевіряє, чи бріф за сьогодні вже є |
| 07:01 | збір, випуск, картка, сторінка, Telegram |
| 04:25 і 05:40 UTC | запасні запуски GitHub — побачать готовий випуск і вийдуть |

Якщо зовнішній сервіс колись впаде, підстраховка спрацює сама. Якщо
навпаки — головний тригер відпрацює. Обидва одночасно бріф не задублюють.

---

## Якщо треба перезапустити руками

Actions → «Ранковий бріф» → **Run workflow**. Залиште поле `source`
як `manual` — тоді випуск зробиться навіть якщо сьогодні вже був.
